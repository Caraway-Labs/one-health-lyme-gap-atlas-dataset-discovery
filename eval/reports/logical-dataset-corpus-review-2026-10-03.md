## What the current graph actually does

`V_CANDIDATE_SUMMARY` and `SnowflakeCandidateReader.list_batch` page by `resource_key`; `CandidateIdentity` requires resource, catalog-dataset and catalog-resource IDs, but the queue and candidate budget count resources. Data registration derives `resource_key` from a canonical resource URL (or catalog-record fallback), while `catalog_resource_id` also includes dataset ID and resource type. `catalog_dataset_id` hashes catalog ID, record ID and metadata hash. Thus `resource_key` identifies a distribution/access record; catalog ID identifies a registered dataset-metadata version, not an enduring cross-version logical identity.

The graph checks exact-resource governed status, observations and at most two deterministic identity links. **Two links cause `AMBIGUOUS_RELATIONSHIP` before classification/model work.** One alternate link bypasses a model relationship call but permits semantic classification and caps any recommendation at LOW; exact duplicate/already known abstain. With this population, **62/107 resources are structurally on the two-link abstention path**, including all 10 county-residence resources. The other 42 linked resources represent 21 two-resource datasets; each sibling can receive a separate semantic classification yet cannot rank above LOW under v1. Three singleton resources have no deterministic link. Thus this batch offers no HIGH/MEDIUM path except those three singleton resources, two of which are non-public VA records and one an unrelated older study. These are code-and-input implications, not observed run outcomes, because the semantic agent was not executed; earlier evidence insufficiency could stop a resource first. The graph does not collapse sibling resources into one recommendation or aggregate their evidence. A one-resource-per-dataset sample alone would still see sibling links in the governed view.

The resource-level boundary is intentional in the v1 contract for source identity, access options, provenance and guarded duplicate handling. Its use as the **primary product recommendation unit** appears poorly matched to this catalog population. A logical-dataset recommendation could retain separate distributions as cited evidence/access choices, and preserve distinct recommendations only where a source-backed edition, geography, time, variable scope, rights condition or independently useful dataset is demonstrated. This proposal must not collapse genuine revisions or equate same-title records across providers. Parent grouping should use stable catalog provider/record identity plus a pinned metadata-version ID, not title alone. This is a proposed decision for owner review, not an implemented contract change.

## Existing path to make the sample runnable, without action in this task

Data stewardship would first approve an exact source/search scope in the existing Data.gov, HealthData.gov or Socrata/ODN discovery configuration, complete a metadata-only discovery run, then invoke the existing `pipeline register-discovery --config-sha256 <checksum>` operation until registration is complete. That operation writes `GOVERNANCE.CATALOG_DATASETS`, `CATALOG_RESOURCES`, and `CATALOG_DISCOVERY_OBSERVATIONS`; the bounded DD summary/observation/identity-link views must then be checked against a `COMPLETED` snapshot. Existing Atlas source definitions or `CURRENT_SOURCE_METADATA_V` rows cannot simply be substituted for DD catalog observations; restricted CDC/NEON evidence must remain safe and source-native. Some NOAA/USGS/NASA products may not be represented in the three configured catalog providers at all. If an approved catalog record cannot be found through the existing pipeline, there is **no demonstrated current path** to put that product in the DD candidate view; any data-owned registration extension needs separate review, not an ad hoc insert or broader agent permission. Pin the resulting run and its observation IDs before paid model use. None of these steps was executed here.

## Decision

**Recommend B, conditional on a balanced governed corpus.** The current resource-level *recommendation* unit makes three large logical datasets consume 46 budget slots and creates an avoidable two-link abstention for 62 resources. Merely selecting one resource per dataset does not remove its sibling links. The single smallest next step is an owner/data-steward review of a **dataset-level candidate projection contract** over already registered catalog identities, with bounded resource evidence/access options and explicit exceptions for genuinely distinct editions or scopes. Do not implement it until that contract and the intended 20–30 logical-dataset sample are approved. A later data-owned discovery/registration pass is also needed because the current completed batch lacks Lyme and environmental positives. No prompt, rank, eligibility, relationship, permission, runtime or scheduling change is justified by this read-only audit.
